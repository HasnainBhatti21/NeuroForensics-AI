# AIF Format Specification

**AIF - Acquisition & Investigation Forensic Evidence Container**
Format version: 1

## 1. Physical format

An AIF case is a **ZIP (Deflate) archive** with the extension `.AIF`.
Entries are written in deterministic order (relative path, sorted) so the
same evidence content always produces the same entry sequence.

File names inside the archive use forward slashes.

## 2. Container layout

```
CASE-XXXX.AIF
├── manifest.json                         evidence manifest (root)
├── case.json                             case metadata document
├── custody.json                          chain-of-custody record
├── memory/                               MemoryCollector artifacts
├── cpu/                                  CPUCollector artifacts
├── gpu/                                  GPUCollector artifacts
├── processes/                            ProcessCollector artifacts
├── network/                              NetworkCollector artifacts
├── windows_events/                       WindowsEventCollector artifacts
│   ├── system/  application/  security/  other/
├── persistence/                          PersistenceCollector artifacts
├── registry/artifacts/                   RegistryCollector artifacts
├── hashes/                               HashCollector artifacts
├── logs/acquisition.log                  full acquisition log
└── reports/acquisition_report.html       in-container HTML report
```

Only folders for executed modules are present. Skipped or failed modules
leave no folder but are documented in `manifest.json` with their reason.

## 3. manifest.json

Root evidence manifest. Fields:

- `case_id`, `case_name`
- `collector`: `{ name, version, build, platform }`
- `host`: `{ hostname, os, os_version, architecture, kernel_version,
  boot_time, username, domain, elevated }`
- `acquisition`: `{ start_time, end_time, operator, method, status }`
  where status is `COMPLETED`, `COMPLETED_WITH_FAILURES`, `PARTIAL`,
  `CANCELLED` or `FAILED`.
- `modules[]`: per-module summary `{ module_id, module_name, status,
  reason, artifacts, bytes, started_at, finished_at, warnings }`.
- `artifacts[]`: one record per acquired artifact:
  `{ artifact_id, relative_path, size, sha256, acquisition_time, source,
  collector, status, notes, synthetic }`.
  `status` ∈ `ACQUIRED | PARTIAL | SKIPPED | FAILED`.
  `synthetic: true` marks DEMO MODE artifacts only.
- `warnings[]`, `errors[]`
- `integrity`: `{ algorithm: "SHA-256", artifact_hashes_in_manifest: true,
  aif_sha256: null }` — see section 5 for why `aif_sha256` is null inside
  the container.

## 4. case.json

`{ format, format_version, case: { case_id, case_name, investigator_name,
organization, evidence_description, acquisition_notes, reference_number,
destination, demo_mode, created_at }, container_sha256: null }`

## 5. Container hash (chicken-and-egg rule)

A container cannot contain its own hash. Therefore:

- Inside the container, `manifest.json` and `case.json` carry
  `aif_sha256: null` / `container_sha256: null`.
- The real container SHA-256 is recorded **externally**:
  - `<CASE-ID>.AIF.sha256` sidecar, format: `<hash>  <CASE-ID>.AIF`
    (sha256sum-compatible),
  - `<CASE-ID>.custody.json` external custody record (`aif_sha256` field),
  - `<CASE-ID>_acquisition_report.html` external report copy.
- Verification (VERIFY AIF) recomputes the container hash from the `.AIF`
  bytes and compares against the sidecar/custody expected value, then
  re-hashes every artifact listed in `manifest.json`.

## 6. custody.json

Chain-of-custody record: `case_id`, `collector_version`, `hostname`,
`operator`, `start_time`, `end_time`, `modules_requested`,
`modules_executed`, artifacts/warnings/errors counters and `aif_sha256`
(external copy only).

Notice embedded in custody documents:
*"Integrity metadata generated by MEMO Collector."*

## 7. Companion files next to the container

| File | Purpose |
| --- | --- |
| `<CASE-ID>.AIF` | Evidence container |
| `<CASE-ID>.AIF.sha256` | Container hash (sha256sum format) |
| `<CASE-ID>.custody.json` | External custody record incl. container hash |
| `<CASE-ID>_acquisition_report.html` | Human-readable report incl. hash |
| `<CASE-ID>.acquisition.log` | Plain-text acquisition log |

## 8. Verification procedure

1. Compare `sha256(<CASE-ID>.AIF)` with the sidecar/custody expected hash
   → container integrity (✓/✗).
2. Open the archive, parse `manifest.json`.
3. For every artifact record, re-hash the entry at `relative_path` and
   compare to the recorded `sha256` → deep artifact integrity.
4. Any mismatch is reported per artifact with expected vs calculated hash.
